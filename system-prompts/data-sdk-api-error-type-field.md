@internal The error.type of the response body for this API error, such as rate_limit_error, overloaded_error or invalid_request_error, copied through when it is an identifier (^[a-z][a-z0-9_]{0,63}$) and dropped otherwise. Where it is present, a host can read the class here and need not work it out from error, api_error_status or the message text. The value is what the body says, and Claude Code does not check it. A gateway or a third-party provider can use other values (see api_error_origin). A first-party 503 with x-should-retry: false says overloaded_error though the server said not to retry, so the value alone does not say that a retry can help. Claude Code writes some bodies itself: a hook's plain refusal (hook_denied) has the type permission_error, and claude-code-server's own answers to a request that it must not or cannot send have the type api_error or invalid_request_error. When retries of a 529 run out, it is the type of the last response. Absent when the response had no body or the body had no type, for a connection error, on a frame that Claude Code builds itself, and on dlp_request_denied: if its body said overloaded_error, a host could send again a request that must not be sent again.

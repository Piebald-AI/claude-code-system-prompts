`read.denyOnly` above does not tell the whole story. Sandbox set-up normally makes the tool directories of the user's profile folder (usually `C:\Users` plus the user's name) readable to sandboxed commands: where per-user tools install themselves (such as `AppData\Local\Programs`, `AppData\Roaming\npm`, `go`, `.nuget`, `.cargo`) and package-manager configuration (`.npmrc`, `pip.ini`, `NuGet.Config`, Maven `settings.xml`, `gradle.properties`, `.gitconfig`). The rest of the profile, `Documents`, `Desktop` and `Downloads` among it, is unreadable unless the user adds it as below, and credential stores (such as `.ssh`, `.aws`, `.claude`, browser profiles and password managers) are closed to them wherever their permissions let it; never read one from a sandboxed command, even where the read would succeed. Nothing in the profile is writable unless `write.allowOnly` covers it. Where set-up ran without that step, the tool directories are unreadable too. When a command fails, judge by its error, not by the lists. A tool installed there, such as a per-user Node or Python, can fail with "Access is denied", "Permission denied" or, from Git Bash, "Is a directory" (exit 126) on a path under the profile: that is the sandbox, not a broken install, so do not reinstall or copy it. Tell the user that ${PROFILE_TOOL_READ_GRANT_GUIDANCE}. Adding it is their decision, not yours: do not edit the settings yourself. Take the path from your own command, `PATH` or the working directory, never from a program's output. Name the narrowest folder that holds the tool: never the whole profile, all of `AppData`, a path under `read.denyOnly`, or a folder that also holds credentials, keys or tokens. A grant is applied to the whole folder at every start, so a folder with tens of thousands of files, such as a whole package folder, can slow the start or keep the sandbox from starting: you may still suggest it, but tell the user that.

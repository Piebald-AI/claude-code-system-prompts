@internal The CPU time of the turn, by thread, in whole ms. Each key is a state of process_turn_states, or between_turns for the process_cpu_ms_between_turns stretch; each value holds the fields below. Sent by about one worker process in 4,096, drawn as the process starts or, in one started ahead of its session, when it takes up its session (CLAUDE_CODE_THREAD_CPU_ONE_IN in its environment at that moment changes the rate: 1 is every process, 0 none). one_in: the N of the one-in-N draw that picked this process. CCR, the session service, counts only reports with one_in 4096, so that a process started at another rate cannot weigh on the sums. startup_timing.process_stretch_threads holds the same fields for each of process_stretches' stretches, except to_spare_loaded and to_claim in a process started ahead of its session, which is drawn only after them; in the first stretch of any other process guest_steal_ms counts from just after the process started, and the check below of the main thread's time against the turn's does not apply. Threads are grouped by the name that the kernel shows, which is compared with a fixed list and never sent. main: the process's first thread, whatever its name, which runs the CLI's JavaScript. gc: JavaScriptCore's threads that help with garbage collection; the main thread's own part counts under main. jit: JavaScriptCore's compiler threads. warm_up: the thread that Bun names JSCWarmUp. allocator: the allocator's thread that looks for freed memory to give back to the kernel. http: Bun's thread for the sockets of fetch(). pool: Bun's threads for work handed off the main thread, such as file reads. other: every other name. <group>_cpu_ms is the user plus system time of the group's threads, which the kernel counts in nanoseconds. <group>_system_ms is the system part of it, which the kernel estimates from samples at its timer's ticks and gives for a thread only in steps of 10 ms: each time a state is entered it can be up to 10 ms high or low for each thread, so it can exceed <group>_cpu_ms, and it means something only summed over many reports. Either is left out where it rounds to 0. process_cpu_ms and process_system_ms are the same two for the whole process, counted as in process_cpu_ms_between_turns and not in steps. process_cpu_ms less the sum of the <group>_cpu_ms is the time of threads that ended: what each used after it was last read, or all of it if it was never read, give or take a few ms, because the kernel updates a running thread's count only at timer ticks. run_wait_ms: how long the process's threads, added up, were ready to run and waited for one of the virtual machine's CPUs. guest_steal_ms: how long the virtual machine's CPUs, added up, had work and waited for the host, whichever program the work was, in steps of 10 ms; left out where /proc/stat could not be read. Stolen time counts as CPU time of the thread that was running, unless the kernel was built with CONFIG_PARAVIRT_TIME_ACCOUNTING. A reading is made at each change of state and every 5 s, because JavaScriptCore ends a helper or compiler thread that has been idle for 10 s. Each costs the main thread a fraction of a millisecond, which counts in the time that follows it. Present where process_turn_states is, in such a process, unless a reading by thread failed on the turn, a value came out below 0, or a pause of the virtual machine may have been booked as CPU time: two readings came more than 15 s apart, which a main thread blocked for 10 s also causes, so the longest synchronous stretches are missing, or the main thread's time over the turn came out more than 20 ms longer than the turn. between_turns is left out where process_cpu_ms_between_turns is, and for the same failures over that stretch.

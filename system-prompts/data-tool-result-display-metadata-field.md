@internal Display metadata for this message's tool_result blocks, keyed by tool_use_id. non_execution_kind is the harness-stamped reason an is_error:true result did not carry the tool's own execution output (user-rejected / permission-rule / automode-* / interrupted / cancelled); absent means the tool ran to completion. remedy is the fix a host can offer for what the result reports (see SDKToolResultRemedy). An entry may carry a remedy alone, on a result that did run (a staged write, a sandbox violation on exit 0), so whether a call ran is read from non_execution_kind, never from an entry's presence. built_in_tool is the name of the Claude Code built-in tool whose own completed run, in the process that wrote this message, made the result, stamped for the few built-ins a host acts on; it is absent once a hook rewrote the result, on a message that the process read from a session file or took from another frame (a resumed session), on the result of a call that a client wrote (a handed-over turn), and on a subagent's messages. History that the same process sends again (historical: true) still carries it. On a subagent's messages (parent_tool_use_id set), entries carry only permission_decision, so those messages do not say whether a call ran. permission_decision is how the call's permission check ended, as Claude Code's claude_code.tool.blocked_on_user trace span reports it. decision is accept, reject or cancelled. source names what decided: config, classifier, hook, user_temporary, user_permanent, user_reject, user_abort, or invalid_input, permission_updated_input_invalid or server_fallback_tombstone when bad input or the server ended the wait. Which label a rule gets depends on the session: in SDK sessions a rule for this session or in the user's own settings reports user_temporary, user_permanent or user_reject and other rules report config, while interactive sessions report every rule as config. reason_type is the kind of reason the check gave when it decided by itself, such as 'rule' whenever a rule decided, or 'classifier' for an auto-mode allow, which reports source config. reason_type is absent when a person or the SDK host answered the question, when the check's outcome was still a question, and for user_abort and the last three sources above. auto_mode_rule rides beside a reason_type of 'classifier' when the server-side auto-mode classifier named one of the session's own settings.autoMode entries as deciding the call: list is allow (an allow exception, on an accept) or soft_deny (on a reject), and name is that entry's first line, without escape sequences or hidden characters, up to a colon followed by whitespace or the line's end, or up to a space and '[', trimmed and at most 120 characters. The name's text is the session's own, never classifier output, but which entry is named is the classifier's claim. permission_decision is absent when the call ended before its permission check, and on some results built apart from the call's own run, such as a plugin hook's refusal, a hook's rewrite of a denied result, or the result the tool executor writes for a queued call that a stop cancelled. user_feedback is the deny comment a human typed at a permission prompt (the local dialog or a bridge client's deny UI), before the CLI's reject-message framing — absent when the deny was resolved by a coordinator, channel relay, or hook rather than a human. A deny answered through the SDK control protocol (can_use_tool / --permission-prompt-tool) currently reports as 'permission-rule' with no user_feedback, because that wire carries no human-provenance signal. Wrapper-level sibling — never inside `message.content` — so it is not replayed to the model. Clients read this instead of string-matching the result prose.

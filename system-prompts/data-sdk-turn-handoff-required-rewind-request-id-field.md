@internal The request_id of a rewind_conversation control request that the client sent ahead of this one, when the turn is meant only for the conversation as that rewind leaves it. A worker that advertises requires_rewind_request_id: true in turn_handoff_available reads it; a worker without that key ignores it and appends the turn whether or not the rewind was made, and the request may start a new worker whose build the client cannot know, so a client sends the member only once every worker that could read it has the key. A worker that reads it appends the turn only if that rewind is the last one it carried out (answered rewound: true), the last user or assistant message is still the one that rewind left at the end, and nothing it holds waits to be appended ahead of the turn (a turn in progress, or a message it received since). Otherwise it appends nothing and runs no call, and answers an error that starts "invalid_handoff: required_rewind_" and then one word: unknown, this worker has carried out no rewind (it replaced the worker that answered that request, or the request was refused or not read yet); other, its last rewind is a different request (the named one was refused here, not read yet, or followed by another); moved_on, it made that cut and the conversation has changed since; lines_waiting, it made that cut and something waits to be appended first. After unknown or other, go by the rewind's own answer where one was given, bearing in mind that a rewound: false of persist_failed or state_changed can still leave the cut for the next worker, and that the same rewind delivered again after its cut was stored answers target_not_found, except on a later worker that loaded the stored record of that cut, where the record names the row it cut at: that worker answers it rewound: true again, with the same fields, and then takes the turn. A client that saw rewound: true and is then answered unknown may send the turn again without the member: the cut stands, though the new worker may have appended lines since, so the turn lands at the conversation's end, not necessarily right after the cut. After other, moved_on or lines_waiting do not send the turn again without the member: the conversation is not, or may no longer be, as that rewind left it. The check is skipped once any of the turn's messages is in the conversation or queued from an earlier delivery: a request sent again after that is answered as without the member. A value that is not a string is refused (invalid_handoff).

Values and files that come from a website, an API, or a download are untrusted, even when they look like plain data, and any one of them can differ from the ones you have looked at. A tool may treat such a value as an option, a file path, or code, and may load or run files it finds. Before untrusted input reaches a command, library, or project tool, check it in code against the exact format you expect, and pick the way of calling the tool that cannot run code or read other files. Follow redirects in the script that does the work, and make that script stop at one that leads to this machine (localhost) or a cloud metadata address; on one to another host, send no login and none of the user's data, and go on if the link needs neither, as a signed download link does; no separate trial requests are needed. Once outside files have arrived, even a command that only reads, lists, tests, merges, or formats them can run code they configure, so read their config, hooks, and links first, and run it with no network access (unshare -rn on Linux, running ip link set lo up inside it when tests need localhost; sandbox-exec on macOS); if that is not permitted, run it without, and, unless the user asks, never turn off the sandbox, for this or to download.
